C1. Concentrate presentation in one deep module

Strong

Files: compare.py, demo.py, cli.py, bundle.py, new render.py

Problem: compare.py owns classification and a 24-line human renderer. Its interface exposes two unrelated jobs. A reader of the verdict model must step through presentation code. demo.py owns a second renderer with the same job. Locality of the presentation concept is low.

Solution: A single render.py module owns render_report and render_demo. compare.py keeps pure classification. Callers import from the one place that owns text. No verdict, exit code, digest, or JSON field changes.

Benefits: Deleting either renderer from its old module concentrates all presentation complexity in render.py. The deletion test passes. Leverage is high: three call sites and the behaviour-lock transcript depend on unchanged text. Tests can assert rendering through one interface. The seam between classification and presentation becomes real with one adapter on each side.

render.py: all text

C2. Extract JSON file helpers from cli.py

Worth exploring

Files: cli.py, possible jsonio.py

Problem: _read_json, _write_json and _check_tag are three small helpers inside the CLI module.

Solution: Move them to a jsonio.py module.

Benefits: Small. The deletion test fails: removing these helpers from cli.py only moves them. Only one adapter exists, so the seam stays hypothetical. Leverage is one call site per helper. Reject for this pass.

C3. Split safety validation out of runner.py

Speculative

Files: runner.py, possible sandbox.py

Problem: runner.py holds subject validation, argv policy, execution and capture. It is the widest module in the codebase.

Solution: Move _validate_subject_tree and _check_command into a sandbox.py module behind a single prepare() interface.

Benefits: Two adapters exist (cli.record and bundle.reproduce), so the seam is real. Deleting the safety code from runner.py would concentrate policy in one deep module. Warning callout: this touches the code that rounds 3, 4 and 5 fixed. The behaviour lock would still pass, but the cost of a mistake is a sandbox escape. Defer to v2 with dedicated adversarial tests.

after

sandbox.py: policy
runner.py: execute + capture

Top recommendation: C1

C1 has the highest leverage per changed line. It deepens compare.py, gives the presentation concept one home, and leaves every observable behaviour untouched. The manager picked it under the behaviour-lock constraint from the brief. C2 fails the deletion test. C3 is real but moves safety-sensitive code that eight review rounds just hardened.

Grilling outcome: no new glossary term. No ADR conflict. Verification obligations: python3 tests/behavior_lock.py --check, the 36-test unit suite, and all eight review rounds must return the same result before and after the move.
